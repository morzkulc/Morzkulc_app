## 2. Start aplikacji — droga krytyczna

To sekcja o największym wpływie na odczucie „apka się muli" na telefonie. Kolejność zdarzeń przy wejściu na `app.morzkulc.pl`:

```
1. HTML (no-store, zawsze z sieci)
2. 9 × CSS  (108 KB, render-blocking)  ─┐ równolegle
3. theme.js + app_shell.js             ─┘
4. app_shell → modules_registry → 11 modułów (430 KB) + 8 plików core (139 KB)
5. Firebase SDK z gstatic (app + auth + storage)
6. getIdToken(forceRefresh=true)        ← round-trip do securetoken.googleapis.com
7. POST /api/register                   ← cold start funkcji (W1)
8. GET  /api/setup                      ← cold start drugiej funkcji (W1)
9. render dashboardu → 5–7 równoległych żądań API (kolejne cold starty)
```

Punkty 4, 6, 7, 8 są sekwencyjne i każdy blokuje następny.

### W1 — `googleapis` w cold starcie każdej funkcji HTTP

| | |
|---|---|
| Fakt | `functions/src/index.ts:1770` — `import {runTaskById} from "./service/runner"` (import statyczny, poza ciałem handlera). `service/runner.ts:1,3` importuje `getTaskRegistry` oraz `GoogleWorkspaceProvider`; `registry.ts` ma 35 importów tasków; cztery providery (`googleAuth.ts:1`, `googleSheetsProvider.ts:1`, `googleCalendarProvider.ts:1`, `googleWorkspaceProvider.ts:1`) robią `import { google } from "googleapis"` — agregat ładujący klientów wszystkich API Google. To samo dotyczy re-eksportów `index.ts:1759-1763` (triggery, worker jobów, `adminRunServiceTask`). |
| Skala | Wszystkie 65 funkcji `onRequest` dzieli jeden entrypoint `lib/index.js`, więc każda z nich ładuje ten łańcuch. |
| Pomiar (lokalnie, Node 24) | `require("googleapis")` — **769 ms**. `require("./lib/service/runner.js")` — **998 ms**, 1547 modułów w cache. Dla porównania `require("firebase-admin")` — 63 ms. Pakiet `googleapis` w `node_modules` waży 116 MB. |
| Skutek | Cold start dowolnego endpointu (np. `/api/gear/kayaks`) płaci ~1 s wyłącznie za załadowanie kodu, którego ten endpoint nigdy nie użyje. Na wolniejszym vCPU Cloud Run realny narzut jest zwykle 2–4× większy niż lokalnie. Przy 65 osobnych usługach Cloud Run i ruchu rozproszonym w czasie („klub kilkudziesięcioosobowy") **większość żądań trafia na zimną instancję** — to najbardziej odczuwalne pojedyncze opóźnienie w całej aplikacji. |
| Naprawa | (a) `index.ts:1770` → dynamiczny `const {runTaskById} = await import("./service/runner")` wewnątrz handlera `appsScriptSync`. (b) Re-eksporty `index.ts:1759-1763` zamknąć w bramce `FUNCTION_TARGET` (przy deployu zmienna jest pusta i wszystkie eksporty są widoczne dla discovery; w runtime ładuje się tylko kod uruchamianej funkcji). (c) Docelowo w providerach zamienić agregat `googleapis` na pakiety per API (`@googleapis/sheets`, `@googleapis/gmail`, `@googleapis/calendar`, `@googleapis/admin`). |
| Zmiana zachowania | Brak. (a) i (b) to wyłącznie moment ładowania kodu. (c) wymaga testu na środowisku prod (te same wywołania API, inny pakiet). |

## 6. Zasoby statyczne, cache, PWA

### W4 — `no-store` wymusza pełne pobranie 804 KB po każdym deployu

| | |
|---|---|
| Fakt | `firebase.json` ustawia `Cache-Control: no-cache, no-store, must-revalidate` na `/core/**`, `/modules/**`, `/styles/**`, `/index.html`, `/map.html`, `/sw.js`, `/manifest.json`. `scripts/bump-sw-cache.js` podbija `CACHE_VERSION` na znacznik czasu przy **każdym** deployu hostingu (predeploy hook). `sw.js` precachuje 49 plików w `install` (`PRECACHE_URLS`) — łącznie **804 263 B**. |
| Sedno | `no-store` zabrania przeglądarce przechowywania odpowiedzi w cache HTTP. Cache API (używany przez Service Workera) działa niezależnie, więc aplikacja po instalacji działa szybko. Ale gdy po deployu instaluje się nowy SW z nową `CACHE_VERSION`, `cache.add()` dla każdego z 49 plików idzie do sieci i — z powodu `no-store` — **nie może skorzystać z warunkowego zapytania**. Efekt: **804 KB pełnego transferu po każdym deployu, dla każdego użytkownika**, także gdy zmienił się jeden plik. |
| Skutek dodatkowy | Pierwsza wizyta (przed aktywacją SW), tryb prywatny, oraz każdy `hardReloadApp()` (`sw_update.js` wyrejestrowuje SW i czyści cały Cache API) pobierają pełne 804 KB + 108 KB CSS bez żadnej warstwy cache. |
| Naprawa | Z nagłówka dla `/core/**`, `/modules/**`, `/styles/**` usunąć **wyłącznie** `no-store`, zostawiając `no-cache, must-revalidate`. `no-cache` nadal wymusza rewalidację przy każdym użyciu, więc świeżość jest zachowana — ale serwer odpowiada `304 Not Modified` na pliki niezmienione, a przeglądarka używa zapisanej kopii. Re-precache po deployu spada z 804 KB do sumy realnie zmienionych plików. `index.html`, `sw.js` i `manifest.json` zostawić bez zmian. |
| Zmiana zachowania | Brak. Semantyka świeżości zostaje ta sama (`no-cache` = zawsze rewaliduj); zmienia się wyłącznie to, czy niezmieniony plik jest przesyłany ponownie. **To nie osłabia mechanizmu z `project_sw_update_banner`** — wykrywanie nowej wersji opiera się na `sw.js`, który zachowuje `no-store`. |
| Kolejność | Wdrożyć **razem z W2** (leniwe moduły): po W2 lista precache skurczy się do rdzenia, a moduły będą wpadać do cache na żądanie. |

### W17 — ciężkie obrazy

Największe zasoby w `public`: `skrypt_kurs/images/front_cover.png` **602 KB**, `wyjscie_na_nurt.png` 494 KB, `pozycja_w_kajaku.png` 406 KB, `wchodzenie_do_cofki.png` 184 KB, `wychodzenie_z_cofki.png` 175 KB; poradniki sprzętowe `kamizelka-poradnik.webp` 486 KB, `fartuch-poradnik.webp` 455 KB, `rzutka-poradnik.webp` 397 KB, `wioslo-poradnik.webp` 338 KB. Zdjęcia znaków ratowniczych — pięć plików po 250–283 KB (JPG).

Nie są na drodze krytycznej (skrypt kursu i modale poradników ładują się na żądanie), ale PNG-i o wadze 400–600 KB to zwykle zdjęcia zapisane bez konwersji. Naprawa: konwersja `skrypt_kurs/images/*.png` i `*.jpg` do WebP (typowo 60–80 % mniej przy tej samej jakości) oraz dodanie `loading="lazy"` w rozdziałach skryptu, jeśli go tam nie ma. Zmiana zachowania: brak.

### W18 — `maplibre-gl` z zewnętrznego CDN

`public/map.html:7` (CSS) i `:190` (JS) ładują `maplibre-gl@5` z `unpkg.com`. Brak `preconnect` do `unpkg.com` i brak `integrity`. `map.html` ma `no-store`, więc jest pobierany od nowa przy każdym wejściu; biblioteka z unpkg ma własne, długie nagłówki cache, więc sam skrypt jest cache'owany po pierwszym razie. ## 9. Problemy, które pojawią się przy większej skali

Sekcja o zachowaniu aplikacji przy wzroście liczby użytkowników, danych i operacji. Nic z tego nie jest problemem dziś.

### 9.1 Kolekcje rosnące monotonicznie, czytane w całości

Wspólny mechanizm: rekord powstaje, nigdy nie przechodzi w stan „zamknięty" i nigdy nie jest usuwany, a odczyt nie ma dolnej granicy. Koszt rośnie z **historią klubu**, nie z liczbą aktywnych spraw.

| Kolekcja | Rośnie o | Czytana w całości przez | Próg odczuwalności |
|---|---|---|---|
| `gear_reservations` (`status=="active"` na zawsze) | każdą rezerwację sprzętu | lista sprzętu, każda próba rezerwacji, sprawdzanie dostępności (W6) | ~2–3 tys. rezerwacji, czyli 3–5 sezonów przy obecnym tempie |
| `basen_enrollments` (`status=="active"` na zawsze) | każdy zapis na basen | `/api/basen/sessions` — home + moduł Basen (N12) | najszybciej rosnąca z tej listy: kilka zapisów × każdy termin × sezon |
| `basen_kayak_allocations` | każdy przydział kajaka basenowego | j.w. | j.w. |
| `godzinki_ledger` | każde zgłoszenie, wydatek, zwrot, bonus | raport składek, `computeNegativeBalances`, badge admina | dziennik od zawsze; przy 100 osobach × 20 wpisów/rok = 2 tys./rok |
| `basen_godziny_ledger` | każdy zapis/anulowanie/nagrodę | panel godzin basenowych | j.w. |
| `events` (`approved==true`) | każdą zatwierdzoną imprezę | zakładka Imprezy w Kilometrówce | najwolniej — kilkanaście rocznie |
| `service_jobs` | 1–3 dokumenty na rejestrację/zatwierdzenie/powiadomienie | fallback dzienny (z filtrem), ale kolekcja bez TTL | koszt magazynowania i listowania w konsoli |

**Wzorzec naprawy, jeden dla wszystkich:** albo (a) pole daty na dokumencie + `where("<data>", ">=", granica)` z indeksem, albo (b) stan końcowy nadawany nocnym taskiem, tak żeby filtr `status` sam ograniczał zbiór. Wariant (a) nie zmienia danych i jest bezpieczniejszy. Warto to zrobić **raz, spójnie**, zamiast łatać kolekcję po kolekcji.

### 9.2 65 osobnych funkcji HTTP = 65 osobnych zimnych startów

Każdy endpoint to osobna usługa Cloud Run z własną pulą instancji. Instancja wygasa po kilkunastu minutach bezczynności. Przy ruchu klubowym (kilkadziesiąt osób, wejścia rozproszone w ciągu dnia) **większość wywołań trafia w zimny start**. Otwarcie dashboardu dotyka 6–8 różnych endpointów — czyli potencjalnie 6–8 niezależnych cold startów.

Wzrost liczby użytkowników ten problem **łagodzi** (instancje pozostają ciepłe), więc nie jest to ryzyko skalowania, tylko stały koszt obecnej skali. Warianty:
- W1 (Etap 1) — usuwa największy składnik kosztu, bez kosztów finansowych.
- `minInstances: 1` na 2–3 najczęściej używanych endpointach (`registerUser`, `getSetup`, `getGearKayaks`) — skuteczne, ale wiąże się ze stałą opłatą; obecnie `minInstances` nie występuje nigdzie w kodzie.
- Konsolidacja endpointów w jedną funkcję z routerem Express — najskuteczniejsze (jedna ciepła instancja obsługuje wszystko), ale to duża zmiana architektury i kolizja z `firebase.json` `rewrites` oraz z ustawieniami invokera opisanymi w pamięci projektu. **Nie rekomendowane teraz.**

### 9.3 Skanowanie w pamięci zamiast zapytań indeksowanych

Miejsca, gdzie logika pobiera zbiór i filtruje go w JavaScript, świadomie („klub < 200 członków"):
- `kmRankingsHandler.ts:86-95` — ranking konkretnego roku: cała `km_user_stats` + sort w pamięci.
- `getAdminUserActivityHandler.ts:109-111` — wyszukiwanie po frazie: cała `users_active` + filtr w pamięci.
- `registerUserHandler.ts:246-270` — dopasowanie po imieniu i nazwisku: cała `users_opening_balance_26` + pętla (W12).
- `getGearKayaksHandler.ts:141` i `gear_bundle_service.ts:1273` — `limit(500)` na katalogu sprzętu.

Te są bezpieczne do ~kilkuset dokumentów. Twardy próg to `limit(500)` na katalogu — przy przekroczeniu **sprzęt zniknie z listy bez żadnego błędu**. Przy obecnych ~55 kajakach margines jest duży, ale limit jest cichy i warto go pilnować (np. logować ostrzeżenie, gdy zwrócono dokładnie 500 dokumentów).

### 9.4 Kontencja transakcji

`basen_service.ts` — `enrollInSlot`, `cancelSession`, `claimWaitingStudent`, `setEnrollmentKayak` modyfikują w transakcji ten sam dokument `basen_sessions/{sessionId}`. Firestore ogranicza zapisy do jednego dokumentu do ~1/s. Audyt 01.09 ocenił to jako teoretyczne i ta ocena jest nadal aktualna — zapisy rozkładają się w czasie. Ryzyko materializuje się dopiero przy „wyścigu po miejsca" (ogłoszony moment otwarcia zapisów na atrakcyjny termin). Wtedy: rozbić licznik na `enrolledCount` per slot w osobnych dokumentach albo użyć rozproszonego licznika.

Analogicznie `counters/members` (auto-inkrement ID członka) — jeden dokument, ale zapisy tylko przy rejestracji nowego konta.

### 9.5 Frontend przy większej ilości danych

- **Lista sprzętu** renderuje wszystkie karty naraz (`gear_module.js:953` — jeden `innerHTML` z pełną siatką). Przy ~55 kajakach jest to w porządku; przy kilkuset kartach na telefonie pojawi się zauważalne opóźnienie renderu. Zabezpieczenie: `content-visibility: auto` na `.gearCard` (dziś nieużywane w żadnym arkuszu — sprawdzone grepem) — jedna właściwość CSS, bez zmian w JS, pozwala przeglądarce pominąć layout kart poza ekranem.
- **Historia godzinek** ma już `limit(200)` na wyświetlanej liście (`godzinki_service.ts:268`), ale saldo liczone jest ze wszystkich rekordów użytkownika (`getAllRecords`, bez limitu) — rośnie z latami aktywności jednej osoby. Znane z 01.09.
- **Kalendarz basenowy na home** (`render_shell.js:1156-1207`) przebudowuje całą siatkę miesiąca przy każdej zmianie miesiąca (`draw()`), ale operuje na `Map` z już pobranych sesji — bez żądań sieciowych. Skaluje się dobrze.

## 10. Sprawdzone, bez znaleziska

- **Wzorce O(n²)** w `public/modules/**` — brak (potwierdzam ustalenie z 01.09). Lookupy budowane na `Map`.
- **Timery** — jeden `setInterval` w całej aplikacji (`app_shell.js:90`, check aktualizacji SW co 20 min), rejestrowany raz poza funkcją renderującą. `setTimeout` w modułach to jednorazowe opóźnienia UI.
- **CLS (przeskakiwanie layoutu)** — `.gearImgPh` ma `aspect-ratio: 4/3` (`gear.css:301`), a kafelki kalendarza `1/1` (`basen.css:457`), więc miejsce na zdjęcie jest zarezerwowane przed jego załadowaniem. Obrazy kart mają `loading="lazy"`.
- **Strategia Service Workera** — network-first dla nawigacji, cache-first dla statyki, zawsze sieć dla `/api/*` i `/__/*`. Poprawna; problem dotyczy wyłącznie nagłówków (W4), nie samej strategii.
- **Debounce autocomplete akwenów** — `km_module.js:247-257` ma 300 ms i próg 2 znaków. Jedyne pole z realnym zapytaniem API na wpisywanie; w porządku.
- **Kosztowne właściwości CSS** — `backdrop-filter` występuje 6 razy w całym repo, `will-change` zero razy, brak długich animacji. Nie jest to źródło zacinania.
- **Indeksy Firestore** — 20 indeksów złożonych w `firestore.indexes.json`; wszystkie zapytania z `where`+`orderBy`, które przejrzałem, mają pokrycie. Brakujące indeksy to nie jest problem tej aplikacji.
- **Nasłuchiwacze mnożone przy renderze** — poza W11b (`MutationObserver`) nie znalazłem nowych wystąpień wzorca opisanego w 01.09; `basen_module.js` i `km_module.js` mają go już naprawionego.
