## 2. Przyrządy

### 2.1 Backend — `Server-Timing`

`functions/src/index.ts`, funkcja `attachServerTiming` wpięta w `setCorsHeaders` — jedyną funkcję wołaną dokładnie raz przez każdy z 65 endpointów (bezpośrednio albo przez `deps.setCorsHeaders` w `api/*.ts`).

Nagłówek każdej odpowiedzi (także 401/403/500, więc smoke test nie wymaga tokenu):

```
Server-Timing: app;dur=<ms handlera>, cold;dur=<wiek instancji przy 1. żądaniu>, boot;dur=<koszt ładowania modułów>
```

| pole | znaczenie | uwaga |
|---|---|---|
| `app` | czas pracy handlera | to ruszają W13/W14/W15/W20a |
| `cold` | `process.uptime()` przy pierwszym żądaniu instancji; 0 dla ciepłej | **zawyżone**, gdy kontener wstał wcześniej i czekał bezczynnie — zmierzone 32 548 ms zaraz po deployu 23.09 |
| `boot` | koszt załadowania grafu modułów `lib/index.js` (`service/boot_timer.ts`) | **właściwa metryka dla W1a/W1b** — odporna na artefakt powyżej |

Dodatkowo **jedna** linia logu na cykl życia instancji (nie na żądanie):
`logger.info("coldstart", {fn, ms, bootMs})` — pozwala policzyć zimne starty, czego wcześniej nie dało się zrobić w ogóle.

Weryfikacja kanału (wykonana 23.09, wynik pozytywny — Hosting nie zjada nagłówka):
```bash
curl -s -D - -o /dev/null https://app.morzkulc.pl/api/godzinki | grep -i '^server-timing'
# HTTP/1.1 401 Unauthorized
# Server-Timing: app;dur=2.1, cold;dur=32548
```

`/api/*` idzie przez rewrites Hostingu, czyli jest **same-origin** — `Access-Control-Expose-Headers` niepotrzebne. Nagłówek czytamy z `resp.headers`, a **nie** z `PerformanceServerTiming`: Safari na iOS nie implementuje tego API, a telefon jest przedmiotem skargi.

### 2.2 Frontend — `public/core/perf.js`

Zero importów, zero żądań sieciowych, 6,4 KB źródła (2,7 KB po gzip, mniej po brotli). Ładowany **osobnym tagiem** jako pierwszy moduł w `index.html` — gdyby był tylko importem w `app_shell.js`, metryka `ms:jsGraph` byłaby zawsze zerem.

Odczyt na telefonie: **`#/home/perf`** (`core/perf_view.js`, ładowany leniwie — nie może obciążać ścieżki, którą mierzy). Przycisk „Kopiuj JSON" + historia 10 ostatnich przebiegów z `localStorage`.

**Kamienie milowe** (ms od startu nawigacji):

| mark | co kończy |
|---|---|
| `js0` | pierwszy wykonany moduł JS |
| `shell` | cały graf core+modules pobrany, sparsowany, skompilowany |
| `fcp` | pierwsze malowanie (brak na starszym iOS → puste) |
| `redirect` | Firebase SDK z gstatic + `getRedirectResult` |
| `auth` | znany stan logowania |
| `token` | token gotowy |
| `register` / `setup` | odpowiedzi tych endpointów |
| `modules` / `nav` / `view` | zbudowane moduły / nawigacja / szkielet na ekranie |
| `homeReady` | **ekran startowy kompletny** |

**Miary:**

| miara | zakres | co udowadnia |
|---|---|---|
| **`ms:home`** | `t0` → `homeReady` | **GŁÓWNE KPI** |
| `ms:boot` | `t0` → `view` | szkielet na ekranie |
| `ms:jsGraph` | `js0` → `shell` | **W2** (leniwe moduły) |
| `ms:redirectWait` | `js0` → `redirect` | W9 |
| `ms:tokenWait` | `auth` → `token` | **W7** (forceRefresh) |
| `ms:register` / `ms:setup` | między kamieniami | W13 / W8 + zimne starty |
| `ms:firstRender` | `setup` → `view` | budowa modułów i nav |
| `ms:homeFanout` | `home0` → `homeReady` | W15 / W20a + zimne starty 4–6 endpointów |

**Bramka „ekran gotowy":** zbiór oczekiwanych ładowań deklarowany z góry w `renderHomeDashboard` (te same warunki, których używają bloki ładujące), domykany przez `.finally` — błąd sieci też kończy ładowanie ekranu. Watchdog 15 s oznacza przebieg jako nieważny (`timedOut`) zamiast wisieć.

**Rozbicie czasu żądania** — najważniejsza rzecz w całym pomiarze:
```
ms   = net + cold + app
app  ← Server-Timing app;dur
cold ← Server-Timing cold;dur
net  = ms − app − cold     (RTT + proxy Hostingu + kolejkowanie Cloud Run)
```
Bez tego poprawka rzędu 60 ms w `app` tonie w ±2 s wahań zimnego startu.

## 3. Procedura przebiegu (lab)

**Scenariusze:** **A** cache zimny (5 przebiegów), **B** cache ciepły (7), **C** pierwsze wejście po deployu (3).
Raportujemy **medianę + min/max**, nigdy średnią — zimne starty robią długi ogon.

Czyszczenie dla scenariusza A (z konsoli karty `app.morzkulc.pl`):
```js
(async () => {
  const rs = await navigator.serviceWorker.getRegistrations();
  await Promise.all(rs.map(r => r.unregister()));
  const ks = await caches.keys();
  await Promise.all(ks.map(k => caches.delete(k)));
  sessionStorage.clear();
  return "cleared:" + rs.length + "/" + ks.length;
})()
```
Scenariusz B: samo `sessionStorage.clear()` — obowiązkowo, inaczej cache badge'a admina sprawia, że kolejny przebieg pomija `/api/admin/pending` i zestaw żądań przestaje być porównywalny.

**`localStorage` i IndexedDB — NIE czyścić.** Tam siedzi sesja Firebase Auth; pomiar zamieniłby się w test logowania.

> **Uwaga na przyszłość:** dziś `/core/**`, `/modules/**`, `/styles/**` mają `no-store`, więc cache HTTP w ogóle nie działa i scenariusz A da się odtworzyć z samego JS. **Po wdrożeniu W4 to przestanie być prawdą** — wtedy scenariusz A wymaga świeżego okna gościa.

Snippet zrzutu (działa też bez `perf.js` — `homeReadyProxy` liczony post factum z Resource Timing): patrz `perf/snapshot.js` w katalogu pomiarów.

## 6. Czego uczciwie nie udowodnimy

Spisane z góry, żeby później nie sprzedawać szumu jako wyniku:

- **W21** (usunięcie diagnostycznego logu) — efekt w ms poniżej progu pomiaru. Właściwa metryka to wolumen logów i koszt, nie szybkość.
- **W11b** (`observer.disconnect()`) — brak sensownej metryki; to poprawka poprawnościowa (wyciek), nie wydajnościowa.
- **W3** (leniwe CSS) — poprawia FCP („strona się pokazała"), prawie nie rusza `ms:home` („ekran gotowy"). Dwie różne obietnice.
- **W4** (nagłówki cache) — działa **wyłącznie** w scenariuszu C. W A i B efekt to dokładnie zero.
- **W9** (`preconnect`) — może być niemierzalne, jeśli `gstatic.com` nie wysyła `Timing-Allow-Origin` (przeglądarka zeruje wtedy `dns`/`tcp`/`tls`). Do ustalenia w pierwszym zrzucie.
- **W1b osobno od W1a**, **W20a osobno od W15** — nierozdzielne bez osobnych deployów (dlatego robimy osobne).
- **W2 / W3 / W4 / `sw.js`** — wspólny zbiór bajtów; czyste rozdzielenie daje tylko `ms:jsGraph` (wyłącznie W2) i FCP (głównie W3).
- **W14, W15b** — nie dotyczą ekranu startowego; mierzyć wchodząc w moduł Godzinki / Zarząd.
